# Requirements Document

## Introduction

Stage 1 of the AWS integration plan for **New Taipei Youth Compass** builds the zero-cost foundation layer that the AWS engineer needs before any AWS resource exists. It delivers four things: the port Protocol definitions that pin the seam between domain logic and infrastructure, a reusable contract-test harness backed by in-memory AWS fakes, an AWS CDK application skeleton that is synthesized but never deployed, and a set of runnable verification scripts the engineer executes and reads directly to judge whether an AWS account is usable.

The design is shaped by two hard external facts. First, the hackathon organizer hands out a dedicated AWS environment only on the morning of the competition and suspends it afterwards, so the team must be able to take an unfamiliar empty account to a verified stack in one command and pull all data back out before the account disappears. Second, cost matters: this feature deploys nothing, spends nothing, and defers Amazon Bedrock, Amazon SageMaker AI, and Amazon Bedrock AgentCore work to a later stage. Stage 1 only *checks readiness* for those services.

Stage 1 also must not disturb work already delivered by the backend workstream. The port Protocols are published as a proposal for the backend team to adopt or amend, the contract-test harness proves itself against a trivial in-memory reference implementation rather than against unfinished adapters, and the existing test suite must keep passing unchanged.

## Glossary

### Architecture terms

- **Port**: A Python `Protocol` (structural interface) that declares the operations the application needs from infrastructure, without naming any concrete technology. Ports live in `src/youth_compass/ports/`.
- **Adapter**: A concrete implementation of a Port for one technology. `adapters/local/` holds offline implementations (filesystem, SQLite, DuckDB); `adapters/aws/` holds AWS implementations (Amazon S3, AWS Glue, Amazon Athena).
- **Ports_And_Adapters_Rule**: The dependency-direction rule recorded in `docs/07-project-structure.md` section 13. `src/youth_compass/domain/`, `src/youth_compass/application/`, and `src/youth_compass/ports/` are forbidden from importing `boto3`, `aws-cdk-lib`, `constructs`, `moto`, `fastapi`, or any module under `adapters/`.
- **Contract_Test_Suite**: A single reusable pytest suite in `tests/contract/` that asserts behaviour required of every implementation of a given Port. The same suite runs against the local adapter and the AWS adapter so the two are provably interchangeable.
- **Reference_Implementation**: A minimal in-memory implementation of a Port that exists only to prove the Contract_Test_Suite is itself correct and executable before real adapters exist.
- **Provider_Selection**: The configuration-driven mechanism from `docs/01-system-architecture.md` section 6 that chooses which Adapter satisfies each Port, using YAML keys such as `storage.provider: filesystem` or `storage.provider: s3`.

### AWS terms

- **AWS_CDK**: AWS Cloud Development Kit. A framework for declaring cloud infrastructure in a general-purpose language; here Python. Used through the `aws-cdk-lib` and `constructs` packages.
- **CDK_Synth**: The `cdk synth` command. Compiles the CDK Python application into CloudFormation templates on the local disk. It contacts no AWS API for a fully-specified stack, deploys nothing, and costs nothing.
- **CDK_Bootstrap**: A one-time per account-and-region setup that creates a staging Amazon S3 bucket, an Amazon ECR repository, and IAM roles that CDK needs before its first deployment. Its presence is recorded in a CloudFormation stack named `CDKToolkit`.
- **CloudFormation_Template**: The JSON document that CDK_Synth produces, describing the desired AWS resources. Committed snapshots of these documents make infrastructure changes reviewable as text diffs.
- **CloudFormation_Stack_Status**: The lifecycle state CloudFormation reports for a stack. The Preflight_Checker treats only a completed create status or a completed update status as a satisfied CDK_Bootstrap.
- **Snapshot_Test**: A test that compares freshly synthesized CloudFormation_Template output against a stored expected copy, so any unintended infrastructure change fails the test with a readable diff.
- **AWS_Budgets**: The AWS cost-monitoring service. A budget defines a spending threshold and sends an email or notification when forecast or actual spend crosses it.
- **Cost_Allocation_Tag**: A key-value label attached to AWS resources so spend can be attributed per project or environment in AWS billing reports.
- **STS_Caller_Identity**: The response of the AWS Security Token Service `GetCallerIdentity` call, containing the account number, the IAM principal ARN, and a user identifier. It is the cheapest and most reliable way to confirm which credentials and account are in effect.
- **Always_On_Resource**: An AWS resource type billed continuously by the hour regardless of use. For this feature the watched types are Amazon SageMaker AI real-time inference endpoints, Amazon SageMaker AI notebook instances, NAT Gateways, Amazon RDS database instances, and unassociated Elastic IP addresses.
- **Moto**: A Python library that intercepts `boto3` calls and simulates AWS services in memory. It requires no credentials, no network access, and incurs no cost, which makes it the execution environment for the Contract_Test_Suite and for the smoke test in continuous integration.
- **LocalStack**: A container that emulates AWS service endpoints locally over HTTP. It is an optional alternative to Moto for manual exploration.
- **Amazon_Bedrock**: The AWS managed foundation-model service. The competition rules restrict entrants to foundation models from Amazon Bedrock or Amazon SageMaker AI, which makes Amazon Bedrock mandatory for the final submission. Individual models require per-account access to be enabled before use.
- **Secret_Scan**: An automated search over version-controlled files for credential-shaped strings. It reports the file path and line number of each finding without echoing the matched value.

### System names used in acceptance criteria

- **Port_Definitions**: The Python modules under `src/youth_compass/ports/` that declare the Ports. Stage 1 covers nine Protocols across nine modules: `object_store.py`, `catalog.py`, `query_engine.py`, `model_provider.py`, `forecast_service.py`, `checkpoint_store.py`, `event_bus.py`, `clock.py`, and `workflow_runner.py`. The last of these is a proposed ninth module, because `docs/07-project-structure.md` section 7 fixes only eight filenames and omits WorkflowRunner.
- **Contract_Harness**: The pytest fixtures, parametrization plumbing, and shared assertions in `tests/contract/` that let one suite run against many Adapters.
- **Infra_App**: The AWS_CDK Python application rooted at `infra/`.
- **Preflight_Checker**: The command-line program `scripts/aws_preflight.py`.
- **Smoke_Tester**: The command-line program `scripts/aws_smoke_test.py`.
- **Data_Exporter**: The command-line program `scripts/aws_export.py`.
- **Bootstrap_Target**: The `make hackathon-bootstrap` Makefile target and the Makefile targets it chains.
- **Dependency_Manifest**: The `pyproject.toml` file at the repository root.

## Requirements

### Requirement 1: Publish the port Protocols as an amendable proposal

**User Story:** As the AWS engineer, I want the six approved port Protocols written down as real Python interfaces in the agreed file locations, so that I can build AWS adapters against a fixed seam without waiting for the backend team and without either of us guessing at method signatures.

#### Acceptance Criteria

1. THE Port_Definitions SHALL declare one `typing.Protocol` for each of ObjectStore, DataCatalog, QueryEngine, ModelProvider, ForecastService, and WorkflowRunner whose public methods are exactly those recorded in `docs/01-system-architecture.md` section 5 (four for ObjectStore, three for DataCatalog, one for QueryEngine, one for ModelProvider, two for ForecastService, two for WorkflowRunner), using the same method names and the same parameter names as that section, declaring `ModelProvider.generate` as `async def`, and adding no public method that is absent from that section.
2. THE Port_Definitions SHALL declare exactly one Protocol per module, placing ObjectStore in `object_store.py`, DataCatalog in `catalog.py`, QueryEngine in `query_engine.py`, ModelProvider in `model_provider.py`, ForecastService in `forecast_service.py`, CheckpointStore in `checkpoint_store.py`, EventBus in `event_bus.py`, and Clock in `clock.py`, matching the filenames fixed by `docs/07-project-structure.md` section 7.
3. THE Port_Definitions SHALL declare a `typing.Protocol` for each of CheckpointStore, EventBus, and Clock, where CheckpointStore declares a save operation and a load operation keyed by a workflow identifier string with load returning the stored checkpoint or `None` when no checkpoint exists for that identifier, EventBus declares a publish operation and a subscribe operation, and Clock declares one operation returning the current timezone-aware UTC timestamp, with every parameter and every return value explicitly annotated.
4. THE Port_Definitions SHALL decorate every one of the nine Protocols with `typing.runtime_checkable`, so that an `isinstance` check against each Protocol returns True for any object that provides the method names that Protocol declares and False otherwise.
5. THE Port_Definitions SHALL give every port module a module-level docstring that states all three of the following: that the Protocol is a Stage 1 proposal originating from the AWS workstream, that the backend workstream may amend the signatures, and the document and section the signatures were taken from.
6. THE Port_Definitions SHALL import only from the Python standard library, `pydantic`, and modules under `src/youth_compass/domain/`, and SHALL contain no import of any other third-party distribution.
7. IF any `.py` module found by recursive search of `src/youth_compass/ports/`, `src/youth_compass/domain/`, or `src/youth_compass/application/` imports `boto3`, `aws-cdk-lib`, `constructs`, `moto`, `fastapi`, or any module under `adapters/`, THEN THE Contract_Harness SHALL fail the dependency-direction test and report every violation found, each naming the offending module path and the offending import name, rather than stopping at the first violation.
8. WHEN `uv run mypy src apps scripts` is executed, THE Port_Definitions SHALL produce zero reported type errors under the strict configuration recorded in `pyproject.toml`, and SHALL contain no `type: ignore` comment and no `typing.Any` annotation in any Protocol method signature.
9. THE Port_Definitions SHALL express every data structure crossing a Port boundary as a `pydantic` model or as a fully parameterized standard-library type, replacing the unparameterized `dict` shown for the `ObjectStore.put` metadata parameter with `dict[str, str]`, and SHALL express storage locations as scheme-qualified URI strings rather than `pathlib.Path` values.
10. IF a Protocol required by `docs/01-system-architecture.md` section 5 has no filename fixed by `docs/07-project-structure.md` section 7, THEN THE Port_Definitions SHALL declare that Protocol in a module named by the snake_case form of the Protocol name, placing WorkflowRunner in `workflow_runner.py`, and SHALL record that module in its own docstring as a proposed addition to `docs/07-project-structure.md` section 7.
11. THE Port_Definitions SHALL define as a `pydantic` model, inside the port module that references it, every payload type named in `docs/01-system-architecture.md` section 5 that has no existing definition under `src/youth_compass/domain/`, covering QuerySpec, QueryResult, ModelRequest, ModelResponse, ForecastRequest, ForecastResult, TrainingRequest, TrainingRun, IngestionRequest, JobReference, and ApprovalDecision, and SHALL import DatasetMetadata and DatasetProfile from `src/youth_compass/domain/` instead of redefining them.

### Requirement 2: Provide a reusable offline contract-test harness

**User Story:** As the AWS engineer, I want one test suite that any adapter implementation must satisfy, running with no AWS credentials and no cost, so that when I write the S3 adapter in Stage 2 I already have the acceptance criteria and can prove the AWS adapter and the local adapter are interchangeable.

#### Acceptance Criteria

1. THE Contract_Harness SHALL provide, for each Port covered in Requirement 1, a pytest test class that any Adapter is bound to by supplying exactly one fixture returning the Adapter instance, requiring zero edits to the test class body, and SHALL allow two or more Adapters of the same Port to be bound simultaneously so that the same test class executes once per bound Adapter.
2. THE Contract_Harness SHALL include a Reference_Implementation of each covered Port that stores all state in process memory only, creating no file, no directory, and no network connection.
3. WHEN the Contract_Test_Suite runs against the Reference_Implementation, THE Contract_Harness SHALL report zero failed tests, zero errored tests, zero skipped tests, and at least one executed test for every covered Port.
4. WHEN the Contract_Test_Suite runs, THE Contract_Harness SHALL complete without reading AWS credentials from environment variables, from `~/.aws/`, or from an instance metadata endpoint, and without issuing any request to a host other than the local machine.
5. WHERE a Contract_Test_Suite case exercises an AWS service, THE Contract_Harness SHALL route every `boto3` call to Moto rather than to an AWS endpoint.
6. THE Contract_Harness SHALL set `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` to fixed non-empty placeholder values, unset `AWS_PROFILE`, and set `AWS_DEFAULT_REGION` to one fixed region for the duration of each test session, and SHALL restore every one of these variables to its pre-session value when the session ends, whether the session passed or failed.
7. THE Contract_Test_Suite for the ObjectStore Port SHALL assert a round-trip property over payload sizes of 0 bytes, 1 byte, and at least 1 MiB, and over keys of 1 character and at least 256 characters: reading the URI returned by a write SHALL return a payload byte-identical to the payload written, including identical length.
8. THE Contract_Test_Suite for the ObjectStore Port SHALL assert that writing the same key with the same payload twice leaves exactly one readable object whose content is byte-identical to the payload, and that a subsequent `list` of that key's prefix returns that key exactly once.
9. THE Contract_Test_Suite for the ObjectStore Port SHALL assert that `list` with a prefix returns exactly the set of keys written under that prefix, excludes keys written under every other prefix, and returns an empty collection when no key matches the prefix.
10. IF a read is requested for a URI that was never written, THEN THE Contract_Test_Suite SHALL require the Adapter to raise the domain error type declared by the Port, and SHALL fail if any `botocore`, operating-system, or other technology-specific exception propagates instead.
11. THE Contract_Test_Suite for the DataCatalog Port SHALL assert that a registered dataset is retrievable by its identifier with every field value equal to the registered value, and that re-registering the same identifier leaves exactly one retrievable record carrying the later field values.
12. THE Contract_Test_Suite for the QueryEngine Port SHALL assert that an identical `QuerySpec` executed twice returns the same number of rows, identical row values in identical order, and identical column names in identical order.
13. THE Contract_Test_Suite for the QueryEngine Port SHALL assert that a `QuerySpec` naming a table outside the allowlist is rejected with the domain error type declared by the Port, and that no row is returned for that `QuerySpec`.
14. THE Contract_Harness SHALL document, in a README inside `tests/contract/`, exactly three ordered steps to bind a new Adapter to the suite, naming the fixture to implement, the Port test class to bind it to, and the command that executes the suite for that Adapter.
15. WHEN `uv run pytest` is executed at the repository root, THE Contract_Test_Suite SHALL be collected and executed alongside the existing unit and integration suites, and the Contract_Test_Suite portion SHALL complete within 60 seconds when bound to the Reference_Implementation.
16. WHEN `uv run pytest` is executed at the repository root, THE Contract_Harness SHALL leave the pass/fail result of every pre-existing test in `tests/unit/` and `tests/integration/` identical to its result recorded before the Contract_Harness was introduced, with zero previously passing tests failing, erroring, or becoming skipped.
17. WHEN a Contract_Test_Suite case completes, THE Contract_Harness SHALL discard all state created by that case so that the next case observes an Adapter containing zero objects, zero registered datasets, and zero query results, and SHALL produce the same pass/fail result on repeated executions of the suite without any manual cleanup between runs.
18. IF, at test session start, any of `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, or `AWS_PROFILE` holds a value that was not set by the Contract_Harness, or if a `boto3` call during the session is directed at an endpoint not served by Moto, THEN THE Contract_Harness SHALL abort the affected test session with an error indicating that ambient AWS credentials or a non-Moto endpoint were detected, and SHALL execute zero further Contract_Test_Suite cases.

### Requirement 3: Add the AWS development dependencies without touching the runtime dependency set

**User Story:** As the AWS engineer, I want `boto3`, `moto`, `aws-cdk-lib`, and `constructs` available in the development environment, so that I can write adapters, fakes, and infrastructure code while the shipped application keeps its current dependency footprint.

#### Acceptance Criteria

1. THE Dependency_Manifest SHALL add exactly four entries (`boto3`, `moto`, `aws-cdk-lib`, `constructs`) to the existing `[dependency-groups] dev` group, each carrying a lower-bound specifier of the form `>=<major>.<minor>.<patch>` in the same style as the existing dev entries, and SHALL retain the six existing dev entries (`httpx`, `mypy`, `pytest`, `pytest-cov`, `ruff`, `types-pyyaml`) with their current specifiers, yielding a dev group of exactly ten entries.
2. THE Dependency_Manifest SHALL keep the `[project] dependencies` list at exactly its current nine entries (`duckdb`, `fastapi`, `polars`, `pyarrow`, `pydantic`, `pydantic-settings`, `pyyaml`, `typer`, `uvicorn`) with their current version specifiers, and SHALL NOT add any AWS package to that list.
3. WHEN `uv sync --python 3.12 --all-groups` is executed on a clean checkout, THE Dependency_Manifest SHALL resolve every runtime and dev entry within 600 seconds, the command SHALL terminate with a success exit status, and `uv.lock` SHALL contain pinned entries for `boto3`, `moto`, `aws-cdk-lib`, and `constructs`.
4. THE Dependency_Manifest SHALL keep `requires-python = ">=3.12,<3.13"`, `[tool.ruff] target-version = "py312"`, and `[tool.mypy] python_version = "3.12"` unchanged.
5. THE Dependency_Manifest SHALL extend the `[tool.mypy]` configuration so that a `mypy` run includes every `.py` file under `infra/` and `scripts/` in its checked-file set, SHALL keep `strict = true`, and SHALL place a comment adjacent to each remaining entry of the mypy `exclude` list stating the reason for that exclusion.
6. THE Dependency_Manifest SHALL configure `ruff` so that a `ruff check` run reports findings for every `.py` file under `infra/` and `scripts/`, with `line-length = 100` and the rule selection `["E", "F", "I", "UP", "B", "SIM", "RUF"]` unchanged and with neither `infra` nor `scripts` present in `extend-exclude`.
7. WHERE a newly added dependency ships platform-specific wheels, THE Dependency_Manifest SHALL specify a version whose resolution in `uv.lock` provides an installable distribution (wheel or source distribution) for CPython 3.12 on both `linux/amd64` and `linux/arm64`, satisfying the ARM64 requirement in `docs/01-system-architecture.md` section 8.
8. IF `uv sync --python 3.12 --all-groups` reports a version conflict or cannot resolve a newly added dependency for `linux/amd64` or `linux/arm64`, THEN THE Dependency_Manifest SHALL leave `uv.lock` unmodified and the failure SHALL be reported through a non-zero exit status with output identifying the conflicting package and the constraint that could not be satisfied.
9. WHEN the environment is installed with the dev group excluded, THE Dependency_Manifest SHALL produce an environment in which none of `boto3`, `moto`, `aws-cdk-lib`, or `constructs` is installed.
10. THE Dependency_Manifest SHALL leave every configuration block not named in criteria 1, 4, 5, and 6 — including `[project.scripts]`, `[build-system]`, `[tool.hatch.build.targets.wheel]`, `[tool.pytest.ini_options]`, `[tool.coverage.run]`, `[tool.coverage.report]`, and `[tool.ruff.lint.per-file-ignores]` — unchanged, so concurrent backend-workstream edits to this shared file are not overwritten.

### Requirement 4: Provide a CDK application that synthesizes cost controls and deploys nothing

**User Story:** As the AWS engineer, I want a CDK app with environment separation, mandatory tags, and a budget stack that I can synthesize and review locally, so that the day the real account appears I deploy known-good infrastructure instead of writing it under time pressure.

#### Acceptance Criteria

1. THE Infra_App SHALL be a Python AWS_CDK application rooted at `infra/` with a single entry point that `cdk synth` can execute and that terminates with a zero exit status when every required context value is present.
2. THE Infra_App SHALL define exactly three named context environments, `dev`, `demo`, and `hackathon`, and SHALL bind to each one a stack name prefix of 1 to 32 characters, a value for every Cost_Allocation_Tag named in criterion 6, and one monthly budget threshold expressed in USD.
3. THE Infra_App SHALL set the monthly budget threshold to 10 USD for `dev`, 20 USD for `demo`, and 50 USD for `hackathon`.
4. IF `cdk synth` is invoked with a context environment name that is not `dev`, `demo`, or `hackathon`, THEN THE Infra_App SHALL raise an error naming the supplied value and the three accepted values, SHALL terminate with a non-zero exit status, and SHALL write no CloudFormation_Template.
5. THE Infra_App SHALL default the deployment region to `ap-northeast-1` whenever no region is supplied through CDK context or the environment.
6. THE Infra_App SHALL apply the Cost_Allocation_Tags `Project`, `Environment`, `Owner`, and `CostCenter` to every stack it defines, each with a non-empty value of at most 255 characters, and SHALL set `Environment` to the name of the selected context environment.
7. IF a stack is constructed without a value for any of the Cost_Allocation_Tags named in criterion 6, or with an empty value for any of them, THEN THE Infra_App SHALL raise an error naming each missing or empty tag, SHALL terminate with a non-zero exit status, and SHALL write no CloudFormation_Template.
8. THE Infra_App SHALL define a budget stack containing exactly one AWS_Budgets monthly cost budget whose limit equals the threshold of the selected context environment in USD.
9. THE Infra_App SHALL configure the budget in criterion 8 with notifications to the supplied subscriber address when actual monthly spend reaches 80 percent and 100 percent of the threshold.
10. THE Infra_App SHALL read the budget notification address from a documented CDK context key or a documented environment variable, preferring the context key when both are supplied.
11. IF the budget notification address is absent, empty, or contains no `@` character when the budget stack is constructed, THEN THE Infra_App SHALL raise an error naming both the context key and the environment variable the operator can set, SHALL terminate with a non-zero exit status, and SHALL write no CloudFormation_Template.
12. THE Infra_App SHALL keep the budget notification address out of every file tracked by version control, including the synthesized output directory and the committed expected templates.
13. WHEN `cdk synth` is executed for any of the three context environments with no AWS credentials present in the environment, THE Infra_App SHALL write one CloudFormation_Template per defined stack to the local output directory, SHALL terminate with a zero exit status within 120 seconds, and SHALL invoke no AWS API that creates, updates, or deletes a resource.
14. THE Infra_App SHALL include one Snapshot_Test per stack that synthesizes the stack with a placeholder notification address and compares the resulting template against a committed expected template.
15. IF a Snapshot_Test detects any difference between synthesized output and the committed expected template, THEN THE Infra_App test suite SHALL terminate with a non-zero exit status and SHALL report the resource path of every differing element.
16. THE Infra_App SHALL include an assertion test proving that every synthesized stack carries all four Cost_Allocation_Tags with non-empty values.
17. THE Infra_App SHALL contain no construct for Amazon_Bedrock, Amazon SageMaker AI, or Amazon Bedrock AgentCore.
18. THE Infra_App SHALL include an assertion test proving that the synthesized templates for all three context environments contain zero resources belonging to the Amazon_Bedrock, Amazon SageMaker AI, or Amazon Bedrock AgentCore resource type namespaces.
19. WHEN the Infra_App test suite runs, THE Infra_App SHALL synthesize every stack with an explicit placeholder 12-digit account identifier and the region `ap-northeast-1`, and SHALL complete without reading AWS credentials.
20. THE Infra_App SHALL document in `infra/README.md` every stack it defines, the context keys and environment variables each stack requires, the budget threshold per context environment, and the exact `cdk synth` command for each of the three context environments.

### Requirement 5: Provide a readable account-readiness preflight checker

**User Story:** As the AWS engineer arriving on competition morning with an unfamiliar account, I want a single command that tells me in about ten seconds what works, what is missing, and what to do about it, so that I spend my first minutes fixing real problems rather than diagnosing them.

#### Acceptance Criteria

1. THE Preflight_Checker SHALL be runnable as `uv run python scripts/aws_preflight.py` with no arguments and SHALL accept a `--region` option that defaults to `ap-northeast-1` and applies to every check in the run.
2. THE Preflight_Checker SHALL resolve AWS credentials through the standard `boto3` chain and SHALL report the resolution source it used as exactly one of environment variables, shared credentials file, shared config profile, single sign-on cache, container credentials, or instance metadata, naming the source only.
3. WHEN credentials resolve, THE Preflight_Checker SHALL call STS_Caller_Identity and SHALL report the credential check as pass together with the 12-digit account number, the full principal ARN, and the effective region.
4. IF credentials fail to resolve, THEN THE Preflight_Checker SHALL report the credential check as fail, SHALL print the configuration steps that would supply credentials, SHALL report every remaining check that requires an AWS call with the skip outcome, and SHALL exit with a non-zero status.
5. WHEN credentials resolve, THE Preflight_Checker SHALL query CloudFormation for a stack named `CDKToolkit` in the target region and SHALL report CDK_Bootstrap as pass with the observed stack status when the stack exists in a completed create or completed update status.
6. IF the `CDKToolkit` stack is absent, or exists in any status other than a completed create or completed update, THEN THE Preflight_Checker SHALL report CDK_Bootstrap as fail, SHALL state the observed status or its absence, and SHALL print the `cdk bootstrap` command including the account number and region already discovered.
7. THE Preflight_Checker SHALL confirm reachability of Amazon S3, AWS Glue, Amazon Athena, AWS Step Functions, AWS Lambda, and Amazon_Bedrock in the target region using exactly one read-only list-or-describe call per service, SHALL report one outcome per service, SHALL report a service as fail when its call returns an authorization error or does not complete, and SHALL limit the Amazon_Bedrock outcome to pass or warn.
8. THE Preflight_Checker SHALL probe the permissions Stage 2 requires — Amazon S3 object read and write, AWS Glue database and table creation, Amazon Athena query execution, AWS Step Functions state machine execution, and AWS Lambda function invocation — using only read-only or explicitly dry-run calls, SHALL make no call that creates, modifies, or deletes a resource, SHALL report each probed permission as allowed, denied, or indeterminate, and SHALL report the permission check as fail when at least one permission is denied.
9. WHEN the Amazon_Bedrock model-access check runs, THE Preflight_Checker SHALL report the identifiers of the foundation models the account is permitted to invoke in the target region and SHALL report the check as pass when at least one model is permitted.
10. THE Preflight_Checker SHALL enumerate all five Always_On_Resource types — Amazon SageMaker AI real-time inference endpoints, Amazon SageMaker AI notebook instances, NAT Gateways, Amazon RDS database instances, and unassociated Elastic IP addresses — in the target region using read-only calls, and SHALL report the cost-guard check as pass with a count of zero when no instance of any type is found.
11. IF at least one Always_On_Resource is found, THEN THE Preflight_Checker SHALL report the cost-guard check as warn, SHALL report the identifier, type, and region of every instance found, SHALL state that each resource accrues charges while it exists, and SHALL print the command that removes it.
12. WHERE the `--json` option is absent, THE Preflight_Checker SHALL print results as a table with exactly one row per check, showing the check name, an outcome that is exactly one of pass, fail, warn, or skip, and a single-line detail of at most 120 characters.
13. IF a check outcome is fail or warn, THEN THE Preflight_Checker SHALL print exactly one remediation line for that check naming the command to run or the console action to take that resolves the finding.
14. THE Preflight_Checker SHALL exit with status `0` when no check has the fail outcome, treating warn and skip outcomes as not affecting the exit status, and SHALL exit with status `1` when at least one check has the fail outcome.
15. THE Preflight_Checker SHALL accept a `--json` option that emits, on standard output, a single machine-readable document carrying the same check name, outcome, detail, and remediation values as the table, suppresses the table, and leaves the exit status rules of criterion 14 unchanged.
16. THE Preflight_Checker SHALL apply a per-call timeout of at most 5 seconds and at most 2 retry attempts per AWS call, and SHALL complete the full run within 30 seconds when every AWS call succeeds.
17. THE Preflight_Checker SHALL never print, in table or machine-readable output, an access key identifier, secret access key, session token, single sign-on token, or the contents of a credential file, in whole or in part, and SHALL print credential material by source name only; the account number and principal ARN are not treated as secret values.
18. IF an individual check raises an unexpected exception, exceeds its per-call timeout after the permitted retries, or is throttled, THEN THE Preflight_Checker SHALL record that check as fail with the exception or condition type and a message of at most 200 characters, and SHALL continue running every remaining check.
19. THE Preflight_Checker SHALL be covered by tests that run against Moto and assert the per-check outcome and the exit status for an all-pass account exiting `0`, an account without CDK_Bootstrap exiting non-zero, an account with no credentials exiting non-zero with remaining checks skipped, an account containing an Always_On_Resource exiting `0` with a warn outcome, and an account with no Amazon_Bedrock model access exiting `0` with a warn outcome.
20. IF no foundation model is permitted, or the Amazon_Bedrock model-access call is denied or unavailable in the target region, THEN THE Preflight_Checker SHALL report the check as warn rather than fail, SHALL state that competition rules require Amazon_Bedrock model access before submission, and SHALL leave the exit status unchanged.
21. IF the value supplied to `--region` is not a syntactically valid AWS region identifier, THEN THE Preflight_Checker SHALL print an error naming the `--region` option and the rejected value, SHALL make no AWS call, and SHALL exit with a non-zero status.
22. WHEN every check has completed, THE Preflight_Checker SHALL print a summary reporting the count of pass, fail, warn, and skip outcomes and the total elapsed wall-clock time in seconds.

### Requirement 6: Provide a round-trip smoke test for a deployed stack

**User Story:** As the AWS engineer, I want one command that proves the deployed data path actually works end to end and cleans up after itself, so that I can trust the stack before the demo instead of discovering a broken permission on stage.

#### Acceptance Criteria

1. WHEN `uv run python scripts/aws_smoke_test.py` is executed with no arguments, THE Smoke_Tester SHALL run the full step sequence in Moto mode and SHALL print a line identifying the active mode as Moto before the first step executes.
2. IF the `--real` flag is absent, THEN THE Smoke_Tester SHALL issue zero calls to a live AWS account and SHALL bind every AWS client it creates to Moto for the duration of the run.
3. WHILE running without the `--real` flag, THE Smoke_Tester SHALL report an estimated run cost of `0.00` United States dollars and SHALL report zero billable units for Amazon S3, AWS Glue, Amazon Athena, and AWS Step Functions.
4. THE Smoke_Tester SHALL write a generated payload of exactly 10 records and at most 4 KiB to Amazon S3, read the same object back, and assert that the checksum of the bytes read equals the checksum of the bytes written using the same checksum function for both.
5. THE Smoke_Tester SHALL register a table in the AWS Glue Data Catalog and assert that retrieving the table returns exactly the column names, column types, and column order it registered, with no extra and no missing columns.
6. THE Smoke_Tester SHALL execute an Amazon Athena query against the registered table and assert that the returned row count equals 10 and that every returned field value equals the corresponding value it wrote.
7. IF the Amazon Athena query does not reach a completed state within 60 seconds, THEN THE Smoke_Tester SHALL mark the Athena step failed, SHALL report the elapsed seconds and the 60 second limit, and SHALL continue to the cleanup phase.
8. THE Smoke_Tester SHALL start an AWS Step Functions execution and assert that the execution reaches a succeeded status within a configurable timeout whose default is 120 seconds and whose accepted range is 10 to 600 seconds.
9. IF an assertion fails, THEN THE Smoke_Tester SHALL report which step failed, SHALL print the observed value alongside the expected value, and SHALL continue to the cleanup phase.
10. THE Smoke_Tester SHALL delete every resource it created during the run, including Amazon S3 objects, the AWS Glue table, and Amazon Athena query output, retrying each deletion up to 3 attempts and spending at most 60 seconds per resource.
11. IF cleanup of a created resource fails after 3 attempts, THEN THE Smoke_Tester SHALL print the identifier of the surviving resource and the command that removes it, and SHALL exit with a non-zero status.
12. THE Smoke_Tester SHALL print a table with one row per step showing pass, fail, or skipped, and SHALL print an estimated run cost in United States dollars to 2 decimal places together with the per-unit rate used for each of Amazon S3, AWS Glue, Amazon Athena, and AWS Step Functions.
13. THE Smoke_Tester SHALL constrain the Amazon Athena query so that scanned data stays under a configurable byte limit whose default is 104,857,600 bytes and whose accepted range is 1,048,576 to 1,073,741,824 bytes.
14. IF the Amazon Athena query reports scanned bytes at or above the configured limit, THEN THE Smoke_Tester SHALL mark the Athena step failed, SHALL print the scanned byte count alongside the configured limit, and SHALL continue to the cleanup phase.
15. THE Smoke_Tester SHALL exit with status `0` only when every step is marked pass and every created resource was deleted, and SHALL exit with status `1` when at least one step is marked fail or skipped or at least one created resource survived.
16. THE Smoke_Tester SHALL name every resource it creates with a run-scoped prefix composed of a fixed literal, a UTC start timestamp, and a random suffix of at least 8 characters, using only lowercase letters, digits, and hyphens, with the total resource name at most 63 characters.
17. WHEN `uv run pytest` is executed, THE Smoke_Tester SHALL be exercised end to end in Moto mode, and the test SHALL assert an exit status of `0`, zero surviving created resources, and a duration under 60 seconds.
18. IF the `--real` flag is passed and any of AWS credentials, target region, or a required Stage 2 resource is unavailable, THEN THE Smoke_Tester SHALL print an error naming each unavailable item, SHALL create no resources, and SHALL exit with status `1`.
19. IF the total run duration reaches 300 seconds, THEN THE Smoke_Tester SHALL stop starting new steps, SHALL mark every unstarted step skipped, SHALL run the cleanup phase, and SHALL exit with status `1`.
20. IF a step is marked fail, THEN THE Smoke_Tester SHALL mark every later step that depends on that step's output as skipped and SHALL execute every later step that does not depend on it.

### Requirement 7: Provide a local data export for account suspension

**User Story:** As the AWS engineer, I want to pull every bucket object and every catalog record onto my laptop with one command, so that the organizer suspending the account after the competition does not destroy the team's work.

#### Acceptance Criteria

1. THE Data_Exporter SHALL be runnable as `uv run python scripts/aws_export.py`, SHALL accept a destination directory option, SHALL accept a `--region` option defaulting to `ap-northeast-1`, and SHALL create the destination directory when it does not already exist.
2. THE Data_Exporter SHALL determine which Amazon S3 buckets to export from configuration values or from a repeatable command-line bucket option, and SHALL copy every object in each selected bucket, including objects beyond the first listing page and objects of zero bytes, into the destination directory, preserving each object key as a relative directory path beneath a per-bucket subdirectory.
3. THE Data_Exporter SHALL export, for each AWS Glue Data Catalog database selected by configuration or by command-line option, the database definition and every table definition in that database as JSON documents written beneath the destination directory.
4. THE Data_Exporter SHALL write a manifest into the destination directory listing every object it attempted, recording for each one the source URI, the destination path relative to the destination directory, the byte size, the checksum value Amazon S3 reports for that object, the checksum computed from the local file, and an outcome of exported, skipped, or failed.
5. WHEN a file already exists at the computed destination path and its locally computed checksum equals the checksum Amazon S3 reports for the corresponding object, THE Data_Exporter SHALL skip re-downloading that object and SHALL count it as skipped.
6. IF an object download fails after the permitted attempts, a checksum comparison still differs after the permitted attempts, or a catalog export fails, THEN THE Data_Exporter SHALL record the failure in the manifest with the object or database identifier and the failure reason, SHALL continue with the remaining objects and catalog items, and SHALL exit with a non-zero status.
7. WHEN the export completes, THE Data_Exporter SHALL print the count of exported objects, the total bytes transferred, the count of skipped objects, the count of failures, and the destination path of the manifest.
8. IF a file at the computed destination path has a locally computed checksum that differs from the checksum Amazon S3 reports for the corresponding object, THEN THE Data_Exporter SHALL download that object again, SHALL overwrite the existing file, and SHALL report the differing expected and observed checksum values.
9. WHILE the `--dry-run` option is supplied, THE Data_Exporter SHALL list every object and every catalog item that would be exported together with each object's byte size, SHALL print the total byte size of the listed objects, SHALL download no object, and SHALL write no file into the destination directory.
10. THE Data_Exporter SHALL be covered by tests that run against Moto and assert manifest contents for a bucket holding nested keys and a zero-byte object, complete export when object listing spans more than one page, skip behaviour on a second run over an unchanged destination directory, re-download of a destination file whose checksum differs, failure recording with a non-zero exit status when an object download fails, and an unchanged destination directory after a `--dry-run` invocation.
11. IF the destination directory is not writable, or the free space available at the destination is less than the total byte size of the objects to be exported, THEN THE Data_Exporter SHALL report an error naming the destination directory and stating the required and available byte counts, and SHALL exit with a non-zero status before downloading any object.
12. IF an object key cannot be written as a relative path beneath the destination directory, THEN THE Data_Exporter SHALL skip that object, SHALL record it in the manifest as failed with its source URI and the reason, SHALL continue with the remaining objects, and SHALL exit with a non-zero status.
13. IF a single object download or a single catalog read fails, or does not complete within 300 seconds, THEN THE Data_Exporter SHALL retry that operation for up to 3 additional attempts, waiting at least 1 second and at most 10 seconds between attempts, before recording the item as failed.
